**Three corrections to the base proposal, from its own judges, adopted here:**
1. Not a live stream through judging with `CRASH_AT=random` (api, investor, bizdev judges): a bounded batch with deterministic fault points, frozen at 3:15; one live mission at a time after that.

## 3. The improved project on one page

**Name:** DEAD RECKONING (codename kept; `ref-gary-chan-8-steps.md` §V.1: do not spend a minute renaming). On-stage subtitle: **"the trip desk that took N requests this afternoon."**

**One line:** An agent that works a queue of trips all afternoon, gets killed at random, comes back with nothing local, checks its receipts before its plan, re-reads the live web, evicts what died, repairs one step, and keeps its working context the size of the job while the transcript agent beside it keeps growing.

**Story (90 s).** The screen is already alive when we walk up: a ticker says the desk has taken N trip requests since 2:30 and been killed K times; a two-line chart shows the transcript agent's context climbing and ours flat. (Viviana/Tianshu/Saptarshi).** "The prompt is bounded by design, so latency is flat by construction; here are P50/P95 over n calls and the llama-bench prefill/decode table in your hardware-evaluation format. (Saptarshi).** The §4 sentence: compaction would flatten the naive line and we name it as the fair comparator; the compaction item is opaque by the docs' own words (`docs/openai/compaction.md`), so what it kept cannot be queried, and rules are what compaction drops (53%/10%, `WINNING_IDEAS.md` §1); ours is a row per edit. - **Q5 (new), "If the desk is idempotent, why the intent row?"** "The intent row tells the agent it has an unresolved effect to ask about instead of re-execute.
