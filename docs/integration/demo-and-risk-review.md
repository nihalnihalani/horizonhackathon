# Dead Reckoning: integration, demo, and risk review

**Recommendation:** keep Dead Reckoning, using the OpenBot web shell and tenant package for the judge-facing app, a custom Dead Reckoning AG-UI control endpoint, and a separate killable mission-runner child. Adapt OpenMuse task/status/approval/receipt patterns for a DOM UI; do not import its React Native screens. Let the runner die while the control API, world feed and simulated booking desk remain alive. RawTree is canonical for mission/evidence state; OpenBot PostgreSQL is limited to identity, leases and UI concerns. This keeps reconnect from masquerading as continuity while retaining one scheduler and one mission authority.

The demo is: reserve ferry → kill the worker after service commit → change a campsite while it is down → resume → reconcile the receipt, revalidate the campsite and preserve accessibility. Show typed decisions and let a separate validator determine validity. A transcript alone does not demonstrate continuity.

## Architecture and sponsor boundary

Keep four records distinct: immutable user constraints; versioned evidence with source/time; action intent and service receipt keyed by stable action key; and an itinerary whose steps name required facts/commitments. The runner writes intent before calling the booking service. The service owns simulated reservations and returns a receipt. After a crash between service commit and acknowledgement, the new runner queries by key and records the recovered receipt. An absent receipt in the agent log means “reconcile,” never “book again.” Site closure changes itinerary validity; it does not erase a prior ferry commitment. If a commitment becomes unusable, show it and its separately tracked compensation or unresolved status.

Keep the booking desk as an independent local HTTP service with its own SQLite database and unique `action_key` constraint. Give it `GET /actions/:key`, `POST /book`, and labeled test-only world-edit/clock endpoints. UI and runner access it over the service boundary; RawTree is the mission/evidence authority, not a substitute for the desk’s booking ledger. Effects are simulated; live Nimble facts are not reservations or claims about travel inventory.

Keep sponsor integrations to exactly **Nimble, Liquid AI, and Tinybird RawTree**. Nimble fetches a few official pages and returns cited evidence; show source URL, retrieval time, effective date if stated, and live/cache status. Liquid proposes typed changes and bounded context edits; schema checks and invariants decide whether to apply them. RawTree persistence of evidence, events, complete checkpoints, and measurements is a must-have; restore reads the latest checkpoint and reconciles pending keys. Keep the desk’s receipt store separate. OpenBot and CopilotKit Intelligence are framework/infrastructure dependencies in the selected stack, not extra sponsors; budget their setup and disclose the Intelligence service. Do not add paid maps, email, or payment processing. If a sponsor path is unavailable, label the fixture/replay clearly.

## Use code as presentation material, not as continuity claims

OpenMuse is MIT licensed and demonstrates a cross-platform React Native/web chat surface. `reference/openmuse/apps/mobile/src/chat.tsx` uses CopilotKit headless `useAgent`, queues follow-ups, restores threads, renders typed tool cards, and exposes send/stop states. `agent-ui.tsx` includes task cards, progress, approval labels and worker-offline messaging. Adapt these for trip chat, receipts and Activity; do not assume mailbox, goals, browser-worker or task state fits this mission schema. Its task service/worker lease flow can inform presentation, but booking reconciliation stays in the dedicated service.

OpenBot is MIT licensed, but its README calls it an alpha template, not a published dependency. `server/src/computer/gateway.ts` resolves opaque snapshot refs, checks policy, records audit, then acts; `computer-view.tsx` shows live state and human takeover. Adapt the ordering for precondition check → intent → simulated action → receipt, plus the judge status feed. `channel-chat.tsx` has readiness/history-restore patterns. Its stack requires Docker, Bun, PostgreSQL, a model key, and CopilotKit Intelligence; those services and channel concepts add setup cost. Avoid a direct OpenMuse bridge: its adapter is disabled/unconnected, and OpenBot runtime run returns Intelligence connection metadata, not raw SSE. Direct Bot AG-UI SSE bypasses runtime orchestration.

Do not call stream reconnection or history replay “agent continuity.” OpenBot’s own `server/src/channels/events.ts` says notifications are transient and not replayed; clients refetch authoritative state after reconnect. OpenMuse restores conversation messages, while its durable task service is a separate workflow. In both cases, the app may restore what was said while losing the external effect or the latest world truth. For this demo, show a new runner process starting from durable mission records, querying the booking service, revalidating evidence, and re-running an independent validator. SSE/WebSocket should only animate these durable changes to the screen. A replayed assistant message is not proof of resumed work.

## Two demo cuts

**90 seconds:** 0–10s show the constraint pins and route. 10–17s judge presses “Arm crash” before the ferry action starts. 17–27s runner writes intent, calls desk, and is killed by the hook after desk commit but before RawTree receipt; show process exit, desk `CONFIRMED`, RawTree `RECEIPT MISSING`. 27–37s judge closes the selected campsite in the operator panel, visibly labeled simulated, while the child is down. 37–50s press Resume; the new process restores, queries by key, and records/shows the recovered receipt without a second booking. 50–66s refresh evidence and show Liquid’s typed proposal plus validator result. 66–80s repair the campsite step while preserving ferry and wheelchair constraints; show a blocked reason if no valid candidate exists. 80–90s open the proof strip with the service receipt, changed fact, verdict, and measured values. Spoken claim: “The conversation can be replayed; the mission is reconstructed from state and reconciled against the service.”

**Three minutes:** 0–20s explain the long-horizon failure with no unsourced headline statistic. 20–40s introduce the typed state and the exact simulated/live boundary. 40–130s run the same 90-second interaction, with a little more time on Nimble citations, Liquid proposal validation and the before/after state. 130–155s compare the two arms and show sample counts, failures, actual action attempts/effects, prompt-token counts and recovery time from the harness. 155–175s explain how RawTree supplies checkpoints/evidence and why SSE is only a view. 175–180s close on the three sponsor roles and state that travel booking was simulated. Do not repeat unverified claims that the proposed solution is universally faster, cheaper or more reliable.

## Fair comparison and claims

Compare against a durable transcript/checkpoint baseline with the same planner model, prompt budget, service idempotency, evidence bundle, candidate set, tool permissions, initial state, injected events and crash schedule. Give it the same booking-service lookup capability; otherwise it is a strawman. Label any “blind transcript resume” arm as a weaker ablation. Both arms should process a repeatable request batch so history growth and context cost are measurable; start with a small fixed batch, grow only after end-to-end stability. Report attempted duplicate calls, actual duplicate effects (expected zero with the same idempotent desk), stale actions, valid/blocked outcomes, constraints preserved, total prompt tokens, recovery time, and repeated tool work. Include `n`, failures and ties. Do not borrow illustrative values from prior docs or claim broad performance from a few fixtures.

## Build boundary and risk controls

For a **5.5-hour, four-person build**, use the OpenBot shell only if it starts cleanly at the outset; integration, RawTree persistence, and service smoke tests are a go/no-go in the first 30 minutes. Limit scope to one booking service, exact fault hook, restart/reconcile, small fixed batch for both arms, deterministic world feed, one Nimble fetch, one Liquid schema-constrained proposal, RawTree checkpoints/evidence rows, and route/receipt/verdict screens. Assign owners for service/recovery, sponsor/data, UI/demo, and integration/validation. Agree schemas and action key first. Leave time for two takes and one live rehearsal. Cut optional live browser takeover, auto-restart, arbitrary world editing, multi-agent orchestration and OAuth before dropping the crash boundary, RawTree persistence, or validator.

The **extended plan** can add more batch rows, bounded history compaction, richer evidence panels, a fixture matrix, and recovery latency/token distributions. Remote RawTree setup is required setup, not a stretch; judge-driven browser takeover and concurrency are optional. Auto-restart can obscure process death; show child PID exit and explicit Resume. Keep the operator panel local; expose no arbitrary commands or real booking actions.

Acceptance gates before calling this complete: (1) killing at the exact service-commit/agent-ack gap and restarting yields one service record and a recovered receipt; (2) editing the site while the worker is confirmed down changes the validator outcome; (3) wheelchair/date/budget constraints survive restart and cannot be model-evicted; (4) stale/unknown evidence blocks or revalidates before an affected action; (5) judge can distinguish real Nimble evidence, injected test event, Liquid proposal, validated state, and simulated booking; (6) the transcript baseline uses matched conditions; (7) UI reconnect refetches state and never presents an SSE replay as proof of completion. If any gate fails, narrate the failure or show `BLOCKED`; do not fake a green result.

**Major caveats:** both reference repos are evolving alpha templates, not drop-in travel products. OpenMuse’s CopilotKit Intelligence key and OpenBot’s broader platform introduce setup and hosted-service dependencies; OpenBot also requires a larger Docker/Postgres/Bun stack. Their MIT code is reusable subject to repository notices, but CopilotKit Intelligence is a separate service with its own terms. The reviewed OpenMuse-to-OpenBot adapter is disabled and has no live session bridge. No implementation, end-to-end integration, benchmark, or sponsor credential verification is established by this review.
