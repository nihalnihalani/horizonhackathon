# OpenBot architecture analysis for Dead Reckoning

**Snapshot inspected:** `reference/openbot` at `3c73cf00efba46122dfd0447485e2b61f1d6a2cd` (25 September 2026). This analysis is based on implementation and manifests in that checkout. OpenBot itself is a clean MIT-licensed clone; the workspace has pre-existing unrelated edits (`.gitignore`, `docs/candidates/`, `docs/plan/`), which were left alone. There is no `AGENTS.md` in the workspace or reference tree.

Source links below are pinned to the inspected commit, so the line numbers can be checked against a stable revision. They accompany the local paths and describe code actually present, not future plans.

## What is implemented

OpenBot is a React/Vite surface, Hono server, PostgreSQL store, CopilotKit runtime, pluggable AG-UI agent endpoints, and an optional isolated Chromium “computer”. The runtime and AG-UI endpoints are deliberately separate. The browser sends a run to `/api/copilotkit`; the server loads the signed-in user's authorized Bot profile and routes to a built-in or remote endpoint. The agent returns AG-UI stream events; the chat surface and its registered tools render/execute them. The architecture flow is documented at [`docs/architecture.md`](../../reference/openbot/docs/architecture.md), and the product route is mounted in [`server/src/app.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/app.ts#L1150-L1179).

The principal reusable idea for Dead Reckoning is not “merge OpenBot into the hackathon app.” It is to keep the OpenBot shell/runtime if useful and expose one small purpose-built AG-UI agent/service that owns Dead Reckoning's workflow. The format is compatible: OpenBot's worker/framework agents and configured remote agents all receive AG-UI requests. The OpenBot managed endpoint itself reads `BOT_PROVIDER=openai|anthropic|google`, provider key/base URL, model, optional OpenAI Responses API and reasoning effort; the LangGraph integration chooses Responses API for GPT 5.6+ because those models need it for tool use. These behaviors and startup checks are in [`agent-langgraph/src/index.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/agent-langgraph/src/index.ts#L56-L220), rather than being inferred from the docs. This is transport compatibility, not a guarantee that an arbitrary sponsor SDK speaks AG-UI or supports the same function-call/stream protocol; put a narrow adapter at the agent boundary when one sponsor does not.

### Harness, request, and event protocol

OpenBot’s `worker` package is a small repeating scheduler for routine firings, not the model execution process. The actual model harnesses live in `agent-langgraph`, `agent-langgraph-agui`, `agent-pydantic-ai`, `agent-crewai`, and other `agent-*` directories. The server supports built-in and remote agents. The fintech package shows the YAML form: an entry has `id`, display metadata, `type: remote-ag-ui`, and `endpoint` (interpolated environment variable); see [`examples/fintech/agents.yaml`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/examples/fintech/agents.yaml#L61-L92). In package loading, the fields are parsed into rows, then `registeredAgentFromRow` turns stored endpoint configuration into a registered remote agent; see [`server/src/copilot.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/copilot.ts#L225-L265). Runtime loading filters agents against the requesting actor's reachability, resolves remote credentials per run, and adds the managed-agent token only for an endpoint that is actually this deployment's own; see [`server/src/agents/runtime-agents.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/agents/runtime-agents.ts#L16-L92). The API allows an authenticated user to test and register a remote URL, but applies endpoint and redirect checks to prevent SSRF and credential/run-assertion leakage; [`server/src/agents/endpoint.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/agents/endpoint.ts#L63-L113) and lines 206-234 explain/check every redirect.

The LangGraph harness builds model tools from the incoming `RunAgentInput.tools`; it does not have its own product-specific tool catalog. It streams message deltas and calls in AG-UI vocabulary (`TEXT_MESSAGE_*`, `TOOL_CALL_*`, `RUN_FINISHED`/`RUN_ERROR`), handling fragmented args, closing a text segment before a tool event, preserving call/result IDs, and returning a visible fallback for an empty model reply. See [`agent-langgraph/src/stream.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/agent-langgraph/src/stream.ts#L41-L235). `history.ts` translates AG-UI history, handles unanswered frontend calls with a synthetic “no answer” tool result, and folds multiple system messages for strict providers; these are useful compatibility lessons for sponsor adapters, not code that should be copied without understanding the framework contract: [`agent-langgraph/src/history.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/agent-langgraph/src/history.ts#L36-L180).

The server's separate plan/handoff consumer demonstrates strict acceptance of only known AG-UI event types and only offered tool names. It ignores state and unrelated events rather than treating remote state as authoritative. See [`server/src/agents/plan-model.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/agents/plan-model.ts#L344-L427). Thus, for a Dead Reckoning status card, use the app's known tool renderer or supported generative UI/A2UI path, or put structured content into the result of a named tool. Do not assume an arbitrary custom AG-UI event/state payload will render or persist. OpenBot's custom components are frontend tools registered in `CopilotProvider` (gallery, sandboxed components, skill/Bot authoring, computer, handoff, ask-person), while server-side tool execution has its own grant/policy boundary: [`app/src/lib/copilot/provider.tsx`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/app/src/lib/copilot/provider.tsx#L31-L79).

For a fixed hackathon status card, the compiled gallery is the stable extension seam: [`app/src/lib/copilot/gallery-registry.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/app/src/lib/copilot/gallery-registry.ts) discovers `components/gallery/*.tsx` files exporting `GALLERY`; a component can register a decision or tool renderer and then be published/granted. Prefer this known typed path over user-authored sandboxed JSX for mission/booking facts. The current channel chat primarily follows messages and run status; if custom AG-UI `STATE` is used, check the channel surface's state subscription/update path explicitly. A persisted API query keyed by trip/reservation is safer for a resumable status panel.

### Persistence, retries, and crash gap

OpenBot PostgreSQL owns identity, access/control, audit, grants, and operational metadata such as durable jobs. Conversation history and memory are **not** in its local database: the configured CopilotKit Intelligence service owns durable threads/memory. `.env.example` says the server requires Intelligence API URL, websocket URL, project API key, and refuses a no-Intelligence degraded mode; it notes self-hosted Intelligence is an Enterprise Helm deployment. Its browser provider keeps the key/license on the server. See [`.env.example`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/.env.example#L111-L133) and [`app/src/lib/copilot/provider.tsx`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/app/src/lib/copilot/provider.tsx#L17-L55). This is a real external-service/licensing/setup gate for reuse, not an optional local worker. For Dead Reckoning, RawTree owns canonical mission and evidence state; the simulated reservation desk owns booking state and idempotency. Neither conversational history nor OpenBot's operational PostgreSQL tables should become the mission source of truth.

The reusable durability pattern is `work_items`: composite `(kind,key)` identity, JSON payload, due time, lease owner/deadline, attempts, terminal time, last error. PostgreSQL `FOR UPDATE SKIP LOCKED` claims work for concurrent replicas; lease timestamps use the database clock; stale leases naturally become claimable; attempts are visible; duplicate offer keys collide; finished rows remain temporarily to suppress duplicates. See [`server/src/db/schema/work.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/db/schema/work.ts#L16-L97), [`server/drizzle/0017_durable_work.sql`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/drizzle/0017_durable_work.sql#L1-L16), and [`server/src/work/queue.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/work/queue.ts#L66-L169). Important limit: this is **at-least-once work delivery**, not exactly-once external effects. Attempt two may mean a previous worker completed an action and died before writing completion (queue comments explicitly call this out at `queue.ts` lines 71-79). Leases and stable job keys alone cannot bridge “reservation committed, receipt not recorded.” Here the simulated reservation desk—not a sponsor integration—owns booking state and idempotency. The mission API should durably record an intent in RawTree's canonical evidence trail before asking the desk to reserve, use the intent's stable key at the desk, and persist the resulting desk receipt/reference. On restart, the single-writer runner must reconcile with the desk by that key/reference before retrying. The campground-close-after-reservation case should recover the already-committed booking, then run Nimble revalidation, Liquid curation, and a RawTree evidence checkpoint against recorded facts. Never let retry treat “unknown outcome” as “reservation failed.”

Routine scheduling also shows a useful offer/execute separation. The sweep writes an idempotent due occurrence to the queue before advancing `next_run_at`, then separately claims and dispatches; it has a freshness grace window to avoid replaying an enormous backlog after downtime. See [`server/src/routines/sweep.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/routines/sweep.ts#L122-L209). The development worker catches database blips and retries its next tick; it reuses sweep and queue functions rather than shelling out to a second implementation, and ticks sequentially rather than overlapping; [`worker/src/index.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/worker/src/index.ts#L1-L18), lines 58-84 and 110-170. Production docs instead run a one-shot sweep as an external CronJob. This worker is potentially reusable for periodic stale-intent sweeps, but it only currently dispatches routines; it is not a generic agent worker framework.

### Tools, approvals, and side effects

The durable action boundary in OpenBot is its server-side tool executor. `grantedTools` offers only current grants and calls one store path; the store checks grant, evaluates CEL policy, audits a decision, then contacts the vendor. Refusal and vendor error are distinguished for the model and UI. See [`server/src/plugins/tools.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/plugins/tools.ts#L10-L20) and lines 182-240; architecture/docs describe deny-before-allow fail-closed policy and audit recording. MCP tools are access-controlled, while custom unknown tools default to write effect. This is a good extension seam for exactly three sponsor integrations: expose typed tool schemas, classify effect, authorize, audit, and add idempotency/reconciliation around mutations. Avoid forwarding the whole sponsor catalog to the model; only grant/offer the three needed integrations and validate args in application code.

Human approvals exist as interactive computer-control/secret-entry, skill/Bot authoring confirmation cards, and `ask_person`, but there is no general durable “approve reservation” workflow primitive shown in the code. A person-facing tool can suspend a run and wait for the browser's answer. That is unsuitable as the source of truth for a long-lived booking intent unless its approval request and answer are separately persisted by the Dead Reckoning application. The computer tool path also proves how browser actions are guarded through server gateway and policy; omit it if the hackathon agent does not automate a browser.

### UI parts and what is volatile

Most reusable UI code is tightly coupled to CopilotKit v2 and can be selectively borrowed: conversation transcript/composer and queued drafts in `app/src/components/channels/`; channel reconnect/resync in `app/src/lib/channels/use-channel-events.ts`; tool-card renderers in `app/src/lib/copilot/`; audit views in `app/src/routes/_authed/admin/audit.tsx`; and routine list/status UI. The direct Bot thread uses localStorage for a thread ID, then checks Intelligence that the upstream thread still exists before claiming history is available; [`app/src/lib/copilot/bot-thread.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/app/src/lib/copilot/bot-thread.ts#L5-L21) and lines 59-113. Channel event websockets are deliberately hints: PostgreSQL is authoritative and lost NOTIFYs trigger roster resync after reconnect, not event replay; [`server/src/channels/events.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/channels/events.ts#L4-L18) and lines 119-169. “Activity” pane calls out that its browser-local command view disappears on reload; the server audit trail is the durable evidence. This matters for DR: UI activity and conversation text cannot substitute for transaction receipts/checkpoints.

### Extraction map for this project

| Need | Reuse approach | Source | DR-specific replacement |
|---|---|---|---|
| Browser shell/chat/runtime | Borrow selectively if the existing app can absorb it; keep CopilotKit runtime on server | `app/src/lib/copilot/provider.tsx`, channel components | Add DR case/status tools and compact trip panel |
| Agent protocol | Implement one isolated AG-UI endpoint or a minimal custom endpoint adapter | `agent-langgraph/src/stream.ts`, `server/src/copilot.ts` | Stream only protocol events; status via named tool results or known card renderer |
| Tool boundary | Reuse patterns: narrow schemas, central server execution, grant/policy/audit | `server/src/plugins/tools.ts`, `server/src/computer/gateway.ts` | Three sponsor adapters with typed input, effect policy, stable idempotency keys |
| Durable worker | Borrow queue/lease/attempt ideas only if useful; keep one single-writer runner and do not add a second scheduler | `server/src/work/queue.ts`, `server/src/db/schema/work.ts`, `routines/sweep.ts` | RawTree canonical mission/evidence state; simulated reservation desk owns booking state and idempotency; explicit unknown outcome |
| Transcript/conversation persistence | Intelligence is external and hosted in normal setup; don't make it business DB | `.env.example`, `app/src/lib/copilot/bot-thread.ts` | SQL trip aggregate and immutable checkpoints/receipts |
| UI cards / custom components | Reimplement or selectively adapt an OpenBot renderer; custom AG-UI event is not proven | `app/src/lib/copilot/provider.tsx`, `gallery-tools.tsx`, `sandboxed-tools.tsx` | DR booking/itinerary status widget backed by persisted state |

Recommended architecture for this challenge is the OpenBot shell plus a custom mission API and one single-writer runner, adapting OpenMuse patterns without importing a second scheduler. RawTree owns canonical mission/evidence state, the simulated reservation desk owns booking state and idempotency, Nimble revalidates, and Liquid curates. On recovery, the runner queries the desk with the durable intent key, reconciles its booking state against RawTree's recorded intent/receipt, then runs Nimble revalidation and Liquid curation and appends a RawTree checkpoint from the evidence. A changed campsite availability after the desk confirms a reservation should create an explicit plan adjustment/notification state rather than erase the confirmed booking or retry the reservation.

## Clone, setup, versions, and license

Clone/setup reference commands are `git clone https://github.com/CopilotKit/openbot.git`, `cd openbot`, `cp .env.example .env`, `bun install`, then `npx --yes copilotkit@latest login` and `npx --yes copilotkit@latest project select`, put the resulting `cpk-...` key in `INTELLIGENCE_API_KEY`, add `OPENAI_API_KEY`, and run `bash scripts/start.sh`. That full script brings up Postgres, computer/browser, bots and supervisor via Compose, then API, app and worker. For a minimal app/API trial without Docker bots/computers, `docs/development.md` explicitly says use `bun run dev`; this still means PostgreSQL, migrations, Intelligence setup and model credentials are required. Server `dev` is `bun --env-file=../.env --watch src/index.ts`; app dev is Vite and Vite proxies to server. Example tenant config is `TENANT_PACKAGE_DIR=../examples/fintech` and singleton-admin is a development-only mode. Repository root manifest pins Bun `1.3.14`, private workspace version `0.0.15`, and workspaces only `app`, `server`, `worker`; `agent-langgraph`, `agent-computer`, and `supervisor` are standalone folders, not workspaces. Exact relevant package versions: root `@ag-ui/core` in app `0.0.59`; server `@ag-ui/client` `0.0.59`; app CopilotKit runtime/react `1.70.1`; server Hono `^4.10.0`, Drizzle `^0.45.2`, `postgres` `^3.4.9`; React `19.2.0`; Vite `^7.1.12`. Caveat: standalone `agent-langgraph/package.json` pins its own `@ag-ui/core` and `@ag-ui/encoder` at `0.0.57`, not `.59`, and it is excluded from the root install. Keep that version skew in mind if plugging it into a root `.59` client or prefer one coherent lock/resolved version. Check root [`package.json`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/package.json), server/app/agent-langgraph package manifests and `docs/development.md` for exact setup details. The full project license is MIT at [`LICENSE`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/LICENSE); preserve copyright/license notices for any copied substantial code and separately respect each dependency's license.

When wiring a local DR endpoint into OpenBot, use the narrow allowlist `AGENT_ENDPOINT_ALLOWED_HOSTS=127.0.0.1:4400` (or the actual exact host/port) and register the endpoint in `agents.yaml`; do not set the broader `AGENT_COMPUTER_ALLOW_PRIVATE_HOSTS=true` as a shortcut. The allowlist mechanism is read in [`server/src/config.ts`](https://github.com/CopilotKit/openbot/blob/3c73cf00efba46122dfd0447485e2b61f1d6a2cd/server/src/config.ts#L927-L935) and intended to permit a named local endpoint while preserving the default private-host block.

**Availability boundary:** present features in this report are code-backed above. “Dead Reckoning”, campsite reservation reconciliation, Nimble, Liquid and RawTree are proposed challenge behavior, not OpenBot features. OpenBot's queue does not currently promise exactly-once side effects, its UI approvals are not a durable booking-approval ledger, and remote AG-UI custom state/event rendering is not established by this snapshot.
