# OpenMuse architecture review for Dead Reckoning

Inspected the checked out OpenMuse source at `f5534c77a8c8740cf792ca73b1f7737829fb7518` (origin `CopilotKit/OpenMuse`, MIT). This is a source-based reuse assessment; I did not install dependencies, run services, or change the clone. The checkout has no `AGENTS.md` under the workspace. The application is an alpha, but it contains a useful, self-hosted durable task engine, typed task state, lease-based workers, persisted evidence/artifacts, and a user approval loop. Its default chat and rich-thread persistence are separate concerns and should not be mistaken for durable mission recovery.

## Reuse assessment

OpenMuse is the stronger starting point for the *durable work control plane*: its `AgentTask`, `TaskWorker`, `TaskContext`, `AgentService`, and `Store` form a complete reusable pattern for queued work, checkpoints, progress events, task controls, user input, and receipts. It also has stable JSON record storage with PGlite or PostgreSQL, and a UI for following the worker. OpenBot can still be the browser/computer and conversation shell as the root plan proposes, but it does not remove the need for a Dead Reckoning-owned mission protocol. Reuse licensed source patterns across the boundary, but run one scheduler/worker loop only: either adapt one scheduler or keep one custom mission runner, rather than starting OpenMuse and OpenBot schedulers against the same mission. Use OpenMuse's domain and worker patterns behind a small adapter, not its Google/PDF product workflows wholesale.

The current OpenMuse engine is not sufficient as the crash-proof reservation protocol by itself. A lease recovers a task after process loss, and a checkpoint preserves the last saved state, but an external reservation can commit between the provider call and the next task checkpoint. Its action path does mark a server restart during an approved action as `outcome_unknown`; the generic model-tool cache, however, stores tool results only *after* the external operation returns. That is exactly the intent/receipt gap Dead Reckoning must close. The reservation desk's idempotent key plus a synchronous RawTree intent and authoritative reconciliation endpoint remain essential.

For the hackathon's Vite/React presentation, the lowest-risk reuse is the server/domain pattern and UI interaction concepts. The checked-in client is Expo/React Native with web support, and components use React Native primitives. It would take more adaptation to reuse its screens in a Vite DOM app than to reproduce the few required mission panels with ordinary React. If building an Expo web demo is already accepted, the agent task screens are much closer to ready. OpenBot's React shell can host the bespoke mission cockpit, while a mission service can persist typed records and drive the demo. The app's task system is a proven local design reference; it is not a drop-in recovery engine for the sponsor log.

## Runtime, UI, state, and event flow

The server starts with `readConfig()`, creates the Store, turns interrupted `actions.status=executing` records into `outcome_unknown`, creates the Hono app, then starts the task worker when enabled ([`index.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/index.ts#L6-L25), [`db.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/db.ts#L91-L95)). `/api/agent` gives a workspace snapshot, task routes expose creation/detail/control/input, and `/api/copilotkit/*` routes conversational agent traffic ([`routes.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/routes.ts#L28-L54), [`app.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/app.ts#L138-L144), [`app.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/app.ts#L320-L337)). The client is not the owner of task state. `AgentWorkspaceProvider` fetches `/api/agent` immediately and polls every three seconds while the app is visible; mutations are POSTs followed by a refresh ([`agent-workspace.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/agent-workspace.tsx#L26-L84)).

Task records have typed status, plan steps, evidence, user input, mutable state, attempt count, lease ID/expiry, optional action ID, result/error, and artifact IDs ([`agent.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/packages/domain/src/agent.ts#L3-L55)). `createTask` validates input, assigns a stable idempotency-derived ID when supplied, seeds a plan, records connector ID in state, and persists a queued record ([`service.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/service.ts#L180-L229)). The worker scans due tasks, claims a task with compare-and-swap, assigns a lease, heartbeats the lease, guards each effect/checkpoint against lease loss, records run events, and writes final task state ([`worker.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/worker.ts#L64-L115), [`worker.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/worker.ts#L116-L247)). On restart, an expired `running` lease is eligible for another worker tick, which reruns from the last saved task record; engine tests explicitly demonstrate restoration of a saved checkpoint ([`engine.test.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/tests/engine.test.ts#L70-L99)).

Mission progress is an append-only set of `run-events` plus a mutable task projection. Task detail sorts events by date and returns artifacts and linked browsers/files ([`service.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/service.ts#L155-L178)). The UI's TaskCard summarizes current progress; TaskDetail shows controls, input prompts, review entry points, evidence, run events, and output artifacts ([`agent-ui.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/agent-ui.tsx#L93-L165), [`agent-ui.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/agent-ui.tsx#L268-L441)). This maps well to Dead Reckoning's offline state, epoch, working-memory cards, action history, and receipt roll, but Dead Reckoning should project those screens from typed event/log rows rather than reuse OpenMuse's task-event schema uncritically.

OpenMuse also has a separate AG-UI conversation path. `ConversationAgent` builds streaming AG-UI events and model tools for search, browse, delegation, goals, monitor and memory; tool results render in React Native using `useRenderTool` and specialized mail/browser cards ([`conversation.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/conversation.ts#L90-L235), [`chat.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/chat.tsx#L36-L108), [`mail-tool-card.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/mail-tool-card.tsx#L23-L108)). Rich threads use CopilotKit Intelligence. The main thread ID is stored in SQL, then `connectAgent` reconnects/replays messages; the message history route also persists a conventional `/api/conversation` fallback. Follow-up drafts queue in client memory and serialize one AG-UI run at a time ([`chat.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/chat.tsx#L203-L307), [`conversation-queue.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/conversation-queue.ts#L1-L45)). **Reconnect, streamed event replay, and thread history are UX/history recovery; they do not resume a killed worker from a durable intent, check whether a reservation committed, or revalidate world facts.** The authoritative mission resume must be implemented on server startup from RawTree and the booking desk, independent of the client connection.

## Approval and persistence boundaries

The mature human-approval flow is useful for trip actions that should remain gated. `ActionService.propose` validates an action, records exact arguments, account/connection, optional target version, hash and 30-minute expiry. `decide` verifies the hash, task status, freshness, connection identity and expiry; it atomically claims an approval before calling the provider and then stores success, failure, or `outcome_unknown` ([`actions.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/actions.ts#L39-L100), [`actions.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/actions.ts#L102-L190)). The app tells the user to review the exact action/account, then opens a review sheet; task cancellation invalidates the lease and denies a still-pending linked proposal ([`agent-ui.tsx`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/src/agent-ui.tsx#L433-L440), [`service.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/service.ts#L231-L304)). For this demo, use approval as a pattern for irreversible bookings/refunds, but do not treat OpenMuse `actions` as RawTree's append-only intent protocol or a booking desk authority.

`Store` is a compact owner/kind/id JSONB record store with CAS helpers; it supports embedded PGlite or PostgreSQL, but it does not provide append-only typed mission logs or `argMax` / as-of projections ([`db.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/db.ts#L13-L76), [`db.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/db.ts#L122-L142)). The README explicitly says PGlite cannot be opened by separate processes: if API and task worker are separate processes, configure a shared PostgreSQL `DATABASE_URL` (and shared data files/secrets); otherwise keep the worker in the API process. Keep Store as a local metadata/cache store only if helpful. RawTree should own the mission's durable event rows and restart projection, but it is an evidence/logging and projection layer, not the authority for effects. The simulated booking desk's own ledger is the authority on whether an effect committed; none of the three sponsors authorizes or records that reservation. Record explicit checkpoints and evidence in RawTree; delete the local cache on the crash-demo path to prove the restore source. OpenMuse's artifacts are persisted and idempotently keyed by task ID, a useful projection pattern ([`service.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/engine/service.ts#L592-L610), [README persistence](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/README.md#L130-L136)).

## Dead Reckoning feature mapping and exactly three sponsor integrations

Dead Reckoning has three load-bearing sponsor integrations: **Tinybird/RawTree, Nimble, and Liquid AI** ([project brief](../FINAL_PROJECT.md)). OpenMuse supplies none of these. Its built-in browser worker is not a substitute for Nimble's structured extraction or domain-health evidence, and its LLM backend is not the local Liquid curator. A candidate list/search result is not an integration until it flows through a typed adapter and appears in the mission evidence.

1. **Tinybird/RawTree:** append-only `epochs`, `constraints`, `facts`, `commitments`, `receipts`, `plan_steps`, `context_ops`, and `metrics`; initial mission projection and every write-ahead reservation intent; a restore projection keyed by monotonic mission revision/event ID, plus as-of queries over a stable sequence. Do not rely on timestamp-only `argMax(value, ts)`: equal timestamps or clock skew can select the wrong state. Write complete checkpoints with a monotonic revision, await the RawTree HTTP insert acknowledgement (`inserted: 1`), then smoke-test the actual projection/query visibility; the HTTP acknowledgement alone does not prove query visibility or transactional database semantics. Poll visibility for a bounded interval, then fail closed and block the effect if the checkpoint remains invisible. The visible `intent` must precede the simulated booking desk call. RawTree is the sponsor-provided evidence/projection layer, not transactional truth about effects; only the simulated desk's own ledger says whether a reservation committed. OpenMuse's Store and run-events help structure the control plane, but cannot provide this contract.
2. **Nimble:** use Domain Health to distinguish unreachable from changed sources; extract park rules, ferry timetable, and the team-controlled public status page with CSS parser output; retain Nimble task/request IDs, driver and observed time with each fact. On resume revalidate every prior-epoch volatile fact that remaining steps depend on. The UI can render source-health and fresh/stale fact cards. OpenMuse's `BrowserService.observe` or monitor loop is a generic public-browser mechanism and does not meet the sponsor-specific provenance/trust requirements.
3. **Liquid AI:** call local `LFM2.5-1.2B-Instruct` with constrained JSON for a narrow notice→typed fact patch and keep/evict curator over the bounded working memory. Deterministic validator enforces the non-evictable wheelchair constraint, unresolved intent pinning, freshness, source/date/party scope, and allowed plan transitions; rejected proposals become visible `context_ops` evidence. OpenMuse's model tools and prompt context show tool-schema patterns, but are cloud-model orchestration, not local context curation. Do not send private constraints to the cloud planner; the cloud-facing plan can receive a derived feasibility boolean if using the privacy stretch.

Use one single-writer mission loop. At boot it records an epoch and restores the latest complete RawTree checkpoint by monotonic revision/event ID; the projection must not depend on timestamps alone, which can tie or arrive out of order under clock skew. Reconciliation asks the booking desk about every intent lacking a terminal result before it asks the planner to inspect the plan. Reconcile known outcomes into durable receipts. Mark volatile facts from old epochs stale, check source health, fetch only facts remaining steps depend on, persist provenance, apply Liquid's typed patch, validate invariants in code, and then expose a bounded context to the planner. Before every external effect: write a complete checkpoint and intent at the next monotonic mission revision; await the write response and verify the checkpoint is visible through the restore query using a bounded poll; if it is not visible, block and do not call the desk. Then call the simulated desk with a stable action key and write/verify the durable receipt/result. This is an acknowledged log protocol, not a claim that RawTree provides a transaction with the desk. If killed after desk commit, resume sees the unresolved intent and asks the desk by key—never blindly repeats. A crash-testable armed kill belongs immediately after desk commit and before local receipt handling, as described by the project spec.

The result is a good combination: OpenBot can provide the authenticated browser/chat shell and human handover; OpenMuse contributes a proven task lifecycle, lease/checkpoint/event pattern and task-detail affordances; the custom mission loop owns all sponsor integrations and restart protocol. Because the existing frontend is React Native and the target pitch is a tailored Vite cockpit, use OpenMuse screens as behavior/reference and reuse only framework-neutral domain/service logic where licensing and packaging permit.

## Exact versions and setup

The manifest uses Node `>=22`, `pnpm@11.19.0`; README recommends Node 24 LTS. Root dependency declarations include `@ag-ui/client` and `@ag-ui/core` `0.0.59`, `@copilotkit/runtime` `1.70.1`, `@tanstack/ai` `^0.59.0`, `@tanstack/ai-openai` `^0.23.2`, `@tanstack/ai-anthropic` `^0.18.13`, `@tanstack/ai-gemini` `^0.32.1`, Hono `^4.11.4`, PGlite `^0.3.14`, and TypeScript `~5.9.2`; `pnpm-lock.yaml` resolves them here to TanStack AI `0.59.0`, Hono `4.13.7`, PGlite `0.3.16`, TypeScript `5.9.3` ([`package.json`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/package.json#L1-L49), [`pnpm-lock.yaml`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/pnpm-lock.yaml#L1-L88)). Mobile pins CopilotKit React Native `1.70.1`, Expo `~54.0.0` (lock: `54.0.37`), React `19.1.0`, React Native `0.81.5` ([`apps/mobile/package.json`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/package.json#L1-L45)).

For reproducing the local OpenMuse app, the documented commands are:

```sh
pnpm install --frozen-lockfile
cp .env.example .env
npx copilotkit@latest login
npx copilotkit@latest project select
# Set CPK_INTELLIGENCE_API_KEY in .env (server only)
pnpm dev
# second terminal
pnpm dev:web
```

The README names API `localhost:8787` and web `localhost:8081`; `pnpm dev:web` maps to the mobile package's `web: expo start --web --port 8081` script ([root `package.json`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/package.json#L8-L25), [`apps/mobile/package.json`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/mobile/package.json#L6-L14)). Chat calls require server-side `CPK_INTELLIGENCE_API_KEY` even in sample mode; open-ended model tasks additionally need `AGENT_BACKEND=model`, `MODEL=provider/model-id`, and provider key. Optional browser is a distinct worker requiring `BROWSER_WORKER_URL`, matching 32+ character `WORKER_TOKEN`, and Chromium install or Docker Compose ([README quickstart/config](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/README.md#L62-L115), [`config.ts`](https://github.com/CopilotKit/openmuse/blob/f5534c77a8c8740cf792ca73b1f7737829fb7518/apps/server/src/config.ts#L45-L102)).
