# Devil's Advocate: Dead Reckoning on OpenMuse/OpenBot

## 1. Top 10 ways this plan dies (ranked, probability × damage)

**#1 — Intelligence key wall kills hour 0-1.** OpenMuse: "Every deployment requires `CPK_INTELLIGENCE_API_KEY`... Rich Threads... in every mode" (`openmuse-README.md` L58, L140). OpenBot: server "refuses to start without" `INTELLIGENCE_API_KEY` (`openbot-README.md` L221-227), plus `DATABASE_URL`, `KEY_ENCRYPTION_KEY`. Both require `npx copilotkit@latest login` (opens a browser, needs an account, needs approval) *before* a single line of the actual hackathon idea is written. On conference WiFi with 4 people fighting for one login flow, this is a top-of-funnel blocker at 11:05, not a nice-to-have. **Bites: hour 0 (11:00-11:30), before the "start repo after 11:00" clock even helps you.**

**#2 — Docker is a hard dependency for OpenBot, and effectively required for OpenMuse's "computer."** OpenBot: "Docker, for PostgreSQL and the shipped Bots" (Requirements), `scripts/start.sh` "starts Docker services", full compose stack: app/server/agent-computer/agent-bot/agent-langgraph/supervisor/Postgres+pgvector (Architecture table, 7 services). OpenMuse's Linux workspace/computer feature needs `docker build -t openmuse-computer:local apps/computer` and "The API needs access to the Docker CLI and engine" (README L120-126). Venue WiFi + laptop Docker Desktop cold-starts + image pulls for 7 services is a classic multi-hour sink. **Bites: hour 0-1, resurfaces at demo time if a laptop sleeps/Docker daemon dies mid-event.**

**#3 — Toolchain version mismatch across 4 laptops.** OpenMuse pins `pnpm@11.19.0`, Node `>=22` in package.json but README says "Node 24 LTS" (inconsistent even within the repo). OpenBot pins `bun@1.3.14` exactly ("Bun 1.3.14. The repository pins it in package.json" — prompt.txt L95). Two different runtimes (pnpm/Node for OpenMuse, Bun for OpenBot) if the team actually does "both" (per the plan's "and/or"). A 4-person team means 4 machines, each needing exact-version installs, likely via nvm/volta juggling under time pressure. **Bites: hour 0, and again anytime someone `git pull`s on a mismatched machine.**

**#4 — The plan's own architecture (RawTree event log, typed memory, Liquid curator, proprioception panel, Nimble research) has *zero* natural integration point in either base repo.** Grep evidence: OpenMuse's task/thread persistence is CopilotKit Intelligence + PGlite/Postgres (`apps/server`, `packages/domain`) — there is no external event-log/SQL-recall abstraction to hook RawTree into without forking core server logic. OpenBot's memory line is "Durable threads and memory: conversations survive restarts through CopilotKit Intelligence" (Features) — memory is *owned by Intelligence*, a hosted black box, which is the exact opposite of "explicit mutable state the agent can see and edit" that is the entire hackathon theme. Grafting RawTree/typed-memory/proprioception onto a system whose state already lives inside someone else's hosted service means either (a) running two parallel state systems (confusing, unconvincing on stage) or (b) ripping out Intelligence-based persistence, which is non-optional per both READMEs. **Bites: hour 1-2, when the team tries to wire RawTree capture into the task loop and discovers CopilotKit Intelligence already owns "the agent's context.**

**#5 — Playwright/Chromium browser worker adds another live-dependency failure mode with zero payoff for the theme.** OpenMuse's flagship demo path is `pnpm --dir apps/worker exec playwright install chromium` + `pnpm dev:browser`, a *separate* Node process token-paired to the API (`WORKER_TOKEN` ≥32 chars). This is real infrastructure for a feature ("agent computer / browser") that has nothing to do with long-horizon context management — it's dead weight the team must carry (install, run, keep alive, debug flakiness) that does not advance the actual judged criterion. **Bites: hour 1, and again live on stage if the browser worker crashes mid-demo (this is the #1 named live-demo risk pattern: browser automation over venue WiFi).**

**#6 — OpenBot's own README calls itself explicitly NOT what this team needs: "A template, not a product... every workspace in this repository is private... You take the repository, replace the example tenant package... Everything below describes a starting point, not a finished thing" (L32).** This is CopilotKit's own words admitting OpenBot is scaffolding for *enterprise coworker platforms* (13 configured coworkers, CEL policy engine, SAML/OIDC, audit trails, admin consoles) — not a long-horizon-context research harness. Layering "Dead Reckoning" on it means dragging along an entire unrelated admin/governance surface (`/admin/boundaries`, `/admin/credentials`, `/admin/identity-providers`) that a judge will see in the repo tree and ask about. **Bites: hour 3+ during demo prep, when the README/repo tour reveals 30+ files of enterprise plumbing nobody built or can explain.**

**#7 — 5-hour clock vs. verified test/setup surface area.** OpenMuse's own VERIFICATION.md reports "154 tests," Biome lint, 3 Expo platform exports, a full Docker computer smoke test, a Playwright lifecycle test — i.e., a CI matrix built for a maintained product, not a hackathon fork. Any non-trivial change to shared server code (needed to insert RawTree/typed-memory hooks) risks breaking tests the team doesn't have time to fix, or the team skips tests entirely and ships something CI-red, which a technical judge (Airbyte/LinkedIn engineers) will check via `gh actions` or ask about directly. **Bites: hour 3-4, when someone finally runs `pnpm test` before demo recording and it's red.**

**#8 — Google OAuth / live credentials rabbit hole.** OpenMuse's most "impressive" scripted capability (Gmail/Calendar) requires "Configure a Google OAuth web client... register redirect URI... consent/test-user access" (README L101) — a multi-step external console flow with propagation delays, easy to burn 30-45 min on for a feature irrelevant to the memory-architecture theme. Team will be tempted to demo it because it's the flashiest pre-built OpenMuse feature, pulling focus and time away from the actual judged deliverable. **Bites: hour 1-2 if someone decides "let's show the email thing too."**

**#9 — "Built during the event" originality rule collides head-on with a 2.2K/5.5K-star repo fork.** Playbook rule: "The project must be built during the event (start the repo after 11:00 AM so the commit history shows that)" (HACKATHON_PLAYBOOK.md L22). A fresh commit history that begins with `git clone` + 875 TypeScript files (OpenBot) or the OpenMuse tree already containing 3 apps, 2 packages, full CI, docs/VERIFICATION.md, docs/ROADMAP.md is trivially detectable — first commit diff will show thousands of pre-existing lines authored by CopilotKit engineers over weeks, dated before Sep 25. Judges checking GitHub (standard practice) see this immediately. This is not a gray area; it's the literal rule text. **Bites: hour 5, at judging, as a disqualification or credibility collapse — the single highest-damage risk on this list.**

**#10 — Sponsor-fit dilution.** The plan's actual value proposition to Tinybird/Nimble/Liquid judges (RawTree event log, Liquid curator, Nimble research, proprioception panel) is a thin ~300-line layer sitting on top of ~50K+ lines of unrelated CopilotKit product code (chat UI, browser worker, Docker computer, admin console, Gmail adapters, CEL policy engine). Judges scored 5/10 from Tinybird/Nimble/Liquid will spend their limited demo-viewing time (5:00-7:00 slot, many teams) trying to find the theme-relevant code inside a repo that is 95% something else. **Bites: hour 5, judging — reduces perceived signal even if #9 doesn't sink it outright.**

## 2. Why each judge doesn't give the prize

**Tinybird judge:** "You forked a 5.5K-star enterprise coworker platform and bolted RawTree onto one corner of it as an afterthought event log. Where's the SQL? Show me the `recall(sql)` tool actually querying RawTree live, not a screenshot. And why does your repo have a CEL policy engine, an audit trail, and 13 preconfigured 'coworkers' that have nothing to do with the event-sourcing pitch? I came here to reward the best use of RawTree as an agent's memory, not the best README description of RawTree wedged into someone else's product."

**Nimble judge:** "Your web-search integration is one tool call buried inside a task engine that already does browser automation (Playwright), Docker containers, and Gmail OAuth — none of which is Nimble. I can't tell if Nimble is load-bearing or decorative, and the fact that your base repo already ships its own 'browser worker' and 'agent computer' tells me Nimble's Search/Extract/Crawl is competing with, not complementing, your foundation's native capability. Show me confidence-graded claims driving a persist/discard decision live, not a config flag."

**Liquid judges:** "Your pitch is 'the big model thinks, the small model remembers, on-device, for ~$0' — but your foundation requires a hosted CopilotKit Intelligence API key 'in every mode' for conversation persistence. That's the opposite of edge/local. If Intelligence owns memory and threads, what is LFM2.5 actually curating that Intelligence isn't already storing? Prove the local model is in the critical path, not a side decoration you added for the prize category."

**OpenAI architect (Saptarshi Banerjee):** "The brief is about Responses API conversation state and compaction. You didn't build a compaction strategy — you inherited someone else's persistence layer (CopilotKit Intelligence, a hosted third-party service you don't control or fully understand) and tried to duct-tape a second, competing state system (RawTree + typed memory) next to it. That's two sources of truth for 'what the agent remembers,' which is the exact failure mode long-horizon-agent research warns about. Also: is this a thin wrapper around Intelligence's own conversation persistence with a dashboard on top? Convince me it isn't."

## 3. "Built during the event" / originality problem

Judges will look at the GitHub repo's commit graph and file tree within the first 30 seconds. A fork of OpenMuse (2.2K stars, alpha, CopilotKit-authored) or OpenBot (5.5K stars, "Trendshift #3 Repository of the Day", 875 TS files) shows an unmistakable signature: a large initial commit or a fork-point far predating 11:00 AM Sep 25, dozens of pre-existing directories (`apps/mobile`, `apps/computer`, `packages/backends`, `examples/fintech/agents/`), CI badges, a VERIFICATION.md dated Sep 16, and a ROADMAP.md — none of which a 4-person team writes in minutes. The playbook rule is explicit and unambiguous: "start the repo after 11:00 AM so the commit history shows that" (L22). This is not a soft "spirit of the rule" issue; it's a literal, checkable fact judges can verify with `git log --reverse | head`.

**Indefensible:** `git clone` (or GitHub "fork") of OpenMuse/OpenBot as the repo submitted, with the hackathon's code added as a thin layer of new files/commits on top. Any judge who clicks "Insights → Contributors" or the initial commit sees CopilotKit's name, not the team's, and sees the codebase already existed. This reads as either misunderstanding or violating the rule — worst case, disqualification; best case, a credibility hit that colors every other judgment.

**Defensible (if attempted at all):** vendoring only the specific, small piece actually needed (e.g., the CopilotKit React headless-chat *client library* as an npm dependency, not the repo) into a fresh repo created after 11:00, with a README that discloses "UI built with `@copilotkit/react-core` (published package), backend/state architecture original to this hackathon." Using a published library via package manager is normal and expected (like using React or Express); cloning and modifying an entire pre-built product is not. The line is: **dependency = fine, fork-as-foundation = not fine**, and the rule's plain text supports that reading.

## 4. Time audit (4-person team, quantitative)

| Setup step | OpenMuse | OpenBot | Custom 300-line harness |
|---|---|---|---|
| Clone + install | `pnpm install --frozen-lockfile` (large monorepo, mobile+server+worker+computer deps) ≈ 5-10 min/machine × 4 = 20-40 min | `bun install` (workspaces: app/server/worker) ≈ 5-8 min/machine × 4 = 20-32 min | `npm init` + `npm i openai zod` ≈ 2 min × 4 = 8 min |
| Intelligence account/key (CopilotKit login+project select, browser OAuth, shared team key) | 10-20 min (per-person browser auth, then decide who owns the project) | 10-20 min (same flow) | 0 min |
| Node/pnpm/Bun version alignment across 4 laptops | 10-30 min (pnpm 11.19.0 exact, Node 22 vs README's "24") | 10-20 min (Bun 1.3.14 exact) | 0-5 min (any modern Node/Python works) |
| Docker stack cold start (Postgres+pgvector, agent-computer, agent-bot, agent-langgraph, supervisor, or OpenMuse's optional computer image) | 15-30 min if using the computer feature (image build + Colima context) | 20-40 min mandatory (`scripts/start.sh` brings up full compose stack, health-check loop) | 0 min |
| Auth secrets (`KEY_ENCRYPTION_KEY`, `WORKER_TOKEN`, Google OAuth client/secret/redirect URI for Gmail) | 10-30 min if Gmail/browser used | 5-15 min (KEY_ENCRYPTION_KEY, COMPUTER_TOKEN, SUPERVISOR_TOKEN — mostly auto-generated by start.sh) | 0 min |
| Understanding the codebase enough to find the right integration point (875 TS files for OpenBot; multi-app monorepo for OpenMuse) | 30-60 min minimum for one person to orient before productive edits | 45-90 min (larger, more surfaces: gateway, policy engine, computer supervisor) | 0 min — you wrote it |

Against a 300-minute (5-hour) budget, OpenMuse/OpenBot setup alone can consume **25-64%** of total available time before the team writes a single line of RawTree/Liquid/Nimble integration — the actual judged work. A custom harness (Python or TS, direct SQLite/JSON state file, direct SDK calls to RawTree/Nimble/Liquid endpoints, no auth wall, no Docker) reaches "writing the theme" in under 15 minutes.

## 5. Fatal flaws: cheapest mitigation, worth it?

| Flaw | Cheapest mitigation | Worth it? |
|---|---|---|
| #1 Intelligence key wall | Skip Intelligence entirely; use raw LLM API calls (OpenAI/Anthropic key each team member already has) | Yes — but this means abandoning OpenMuse/OpenBot's core persistence, i.e., abandoning the base itself |
| #2 Docker dependency | Don't run the computer/compose stack at all; use OpenMuse's "local sample app needs no model, Google account, or Docker" path only | Partial — but that's the demo-free skeleton, none of the impressive features |
| #4 No integration point for RawTree/typed memory | Fork nothing; write state management as a standalone module and only use CopilotKit's *published npm client* for chat UI | Yes, this is essentially verdict (d) below |
| #9 Originality violation | Create a brand-new repo at 11:00, `npm install @copilotkit/react-core` as a dependency, write all state/RawTree/Liquid/Nimble logic from scratch | Yes — mandatory, not optional, given the explicit rule |
| #5/#6 Irrelevant surface area (browser worker, admin console, Gmail) | Don't touch these subsystems at all | Trivially yes, but then ask why you forked the repo in the first place |

The pattern is consistent: every mitigation that actually neutralizes the risk converges on **not using OpenMuse or OpenBot as the base at all**, and instead using CopilotKit only as a UI dependency (published package) or not at all.

## 6. Verdict

**(e) Custom harness, no CopilotKit.**

Five hours is not enough to clear Intelligence-key auth, Docker compose cold-start, and Bun/pnpm version alignment across four laptops *and* build a defensible, theme-native RawTree+typed-memory+Liquid+Nimble system *and* survive the "built during the event" originality check on a 5.5K-star fork. Every hour spent orienting inside OpenBot's 875-file enterprise coworker platform or OpenMuse's mobile/browser/computer stack is an hour not spent on the actual judged artifact: a flat context window, a visible persist/discard split, and a crash/resume demo. CopilotKit's own README undercuts the choice directly — OpenBot is "a template... not a finished thing" and OpenMuse's memory is owned by a hosted third-party service, which contradicts the entire "explicit mutable state the agent controls" thesis this hackathon rewards. Build a plain TS/Python harness (state file + RawTree/Nimble/Liquid API calls, a simple web dashboard), skip CopilotKit UI unless someone finishes early, and spend the saved 90+ minutes on the two things that actually win: the baseline-vs-flat-context chart and the `kill -9`/resume demo.

---

**5-line summary:** OpenMuse and OpenBot both hard-require a hosted CopilotKit Intelligence key plus (for OpenBot) a full Docker/Postgres compose stack before any theme-relevant code can be written — audited at 75-190 minutes of setup against a 300-minute clock, versus ~15 minutes for a custom harness. Neither repo has a natural hook for RawTree/typed-memory/Liquid-curator/proprioception, because both already own "memory" via hosted Intelligence, creating two competing state systems that every sponsor judge (Tinybird, Nimble, Liquid, OpenAI) will independently flag as thin-wrapper or off-thesis. The fatal, non-negotiable risk is the "start the repo after 11:00 AM" originality rule: forking a 2.2K–5.5K-star pre-existing product is trivially detectable in the commit history and risks disqualification, not just a weak score. Every viable mitigation for every listed flaw converges on the same fix: don't build on OpenMuse or OpenBot at all. Verdict: (e) custom harness, no CopilotKit — build 300 lines from scratch and spend the saved two hours on the flat-context chart and the crash/resume demo that actually wins.
